# 配置中心重构与渐进式性能优化设计

- 日期：2026-03-15
- 状态：已确认
- 适用项目：Smart Media / quark_strm

## 1. 背景

当前项目已经具备配置中心雏形，但配置能力仍然分散在后端配置模型、配置接口、前端零散卡片和高级 JSON 编辑器之间，导致以下问题：

1. 配置页覆盖不完整，很多应用级配置仍需依赖手工 JSON 或文件编辑。
2. 配置字段的默认值、校验规则、敏感字段策略和页面展示规则没有统一元数据来源。
3. 前后端存在旧格式与新格式并存的兼容逻辑，增加维护成本。
4. 配置页与配置保存链路存在进一步优化空间，但必须保证现有功能逻辑不变。

## 2. 目标

本次重构采用“分层重构 + 配置中心化 + 渐进性能治理”的方案，目标如下：

1. 保持现有主技术栈不变：Python + FastAPI + Vue 3 + TypeScript。
2. 在不改变业务功能逻辑的前提下，完成较大幅度结构优化。
3. 让几乎全部应用级配置都能通过配置页面管理。
4. 保留 `config.yaml` 作为主要持久化来源，并继续支持环境变量覆盖。
5. 每一步优化后都执行最小可行测试，确保项目始终可运行。

## 3. 非目标

本次不主动进行以下改造：

1. 不更换前后端主框架。
2. 不把配置持久化主来源从 YAML 直接切换到数据库。
3. 不推翻现有环境变量覆盖机制。
4. 不做与本次任务无关的大范围清理式重构。
5. 不修改 Docker / GitHub Actions 的基础设施语义，只确保现有 CI 路径不被破坏。

## 4. 当前关键事实

### 后端

- 配置模型集中在 `quark_strm/app/config/settings.py`
- 配置接口集中在 `quark_strm/app/api/system_config.py`
- 配置读写与热加载集中在 `quark_strm/app/services/config_service.py`

### 前端

- 当前配置页位于 `quark_strm/web/src/views/ConfigView.vue`
- 当前前端配置 API 位于 `quark_strm/web/src/api/systemConfig.ts`

### 已有能力

- 已存在完整系统配置读取/保存接口。
- 已存在敏感字段掩码回显与恢复逻辑。
- 已存在 AI model / AI providers 的兼容处理链路。
- 已有配置页相关单测与 E2E 测试基础。

## 5. 最终方案

采用方案 B：分层重构 + 配置中心化 + 渐进性能治理。

### 核心决策

1. 保留当前技术栈与主要接口语义。
2. 优先重构配置契约，再重构配置页，再做性能优化。
3. 对“几乎全部配置都支持在配置页面设置”的要求，解释为：几乎全部应用级配置可页面管理，敏感字段通过安全方式更新，部署级基础设施项不直接由页面接管。
4. 高级 JSON 编辑器保留，但从主入口降级为兜底入口。

## 6. 配置页覆盖范围

### 6.1 纳入配置页的内容

#### 业务配置
- Quark
- TMDB
- Emby
- AI Providers
- WebDAV / AList
- Telegram / WeChat 通知
- Security
- CORS
- Log

#### 运行参数
- 全局 timeout
- 扩展名列表
- 子目录创建策略
- 数据库路径
- endpoint 映射与目录映射等高级运行参数

#### 高级配置
- 保留高级 JSON 编辑器，用于调试兜底、未来字段兼容、导入导出。

### 6.2 敏感字段策略

以下字段不明文回显，但支持安全更新：

- `quark.cookie`
- `emby.api_key`
- `security.api_key`
- `telegram.bot_token`
- `webdav.password`
- `alist.token`
- 各 AI provider 的 `api_key`

处理原则：

1. 页面显示“已配置/未配置”或掩码。
2. 留空表示保留原值。
3. 仅在用户显式更新时写入新值。
4. 不破坏现有掩码字段恢复逻辑。

### 6.3 不直接由配置页接管的内容

以下内容可映射出应用层配置，但不把基础设施本身当作页面直接管理对象：

- Docker / Compose 文件本身
- GitHub Actions 工作流本身
- 容器端口映射机制
- 环境变量注入机制本身

## 7. 兼容性约束

为保证“功能逻辑不变”，本次重构必须遵守以下约束：

1. `config.yaml` 继续作为主要持久化来源。
2. 环境变量覆盖机制继续生效。
3. 掩码字段回填逻辑继续生效。
4. 现有核心业务能力不改变语义：
   - Quark 浏览 / 重命名
   - STRM 生成
   - Emby 集成
   - WebDAV / AList 兜底
   - 通知推送
5. 现有核心配置接口继续兼容：
   - `/api/system-config/`
   - AI models / AI providers 兼容链路尽量保留

## 8. 分阶段实施方案

### 阶段 1：配置契约收敛

目标：先整理配置定义和配置接口，不改业务行为。

主要工作：

1. 为配置字段补齐统一元数据：分组、默认值、敏感标记、展示类型、帮助信息、是否高级字段。
2. 收敛后端配置返回结构与敏感字段策略。
3. 收敛 AI 配置兼容逻辑，减少前端 fallback 分支。
4. 补配置契约相关测试。

主要文件：

- `quark_strm/app/config/settings.py`
- `quark_strm/app/api/system_config.py`
- `quark_strm/app/services/config_service.py`
- `quark_strm/web/src/api/systemConfig.ts`

### 阶段 2：配置页骨架重构

目标：先把页面结构调整到位，再按组逐步接配置字段。

主要工作：

1. 重构 `ConfigView.vue` 为分组配置中心。
2. 拆出最必要的配置分组组件与敏感字段输入组件。
3. 保留高级 JSON 入口，但退为兜底能力。
4. 补配置页单测与 E2E。

### 阶段 3：几乎全部应用配置接入 UI

建议接入顺序：

1. Emby
2. Quark
3. AI Providers
4. WebDAV / AList
5. 通知
6. 安全
7. CORS / 日志 / timeout / 扩展名 / 数据库路径
8. endpoints / dirs 等高级结构化配置

### 阶段 4：性能优化

目标：在配置中心结构稳定后，处理热点性能问题。

重点方向：

#### 前端
- 配置分组按需渲染
- 减少初始化重复请求
- 降低大 JSON 与表单状态相互覆盖的成本
- 拆分过重组件，减少整页重渲染

#### 后端
- 减少配置读取/保存链路中的重复序列化与重复校验
- 优化热点路径中不必要的深拷贝与全量 merge
- 对只读配置元数据进行缓存
- 不改变最终 YAML 落盘行为

### 阶段 5：完整回归

在全部阶段完成后执行一轮完整回归，确保：

1. 配置功能可用
2. 原有核心业务功能不退化
3. 前后端测试与 CI 路径保持正常

## 10. 风险与控制

### 风险 1：敏感字段被误清空

控制方式：
- 留空保留原值
- 掩码值回传恢复旧值
- 用测试覆盖保存前后行为

### 风险 2：大配置对象改造后字段丢失

控制方式：
- 先统一 schema，再做页面改造
- 保留高级 JSON 作为兜底
- 每组字段接入后单独验证

### 风险 3：前端配置页改造引入行为漂移

控制方式：
- 先补测试，再改页面
- 配置页单测 + E2E 双重验证
- 不与性能优化混在同一步执行

### 风险 4：性能优化误伤逻辑

控制方式：
- 把性能优化放在配置中心稳定后
- 只优化热点路径
- 每次优化后立即执行回归测试

### 风险 5：旧 AI 配置 / 新 AI 配置兼容失败

控制方式：
- 前后端同时保留兼容层
- 先收敛契约，再逐步减少分支
- 用旧格式、新格式、混合格式覆盖测试

## 11. 实施顺序结论

最终实施顺序确定为：

1. 配置契约收敛
2. 配置页骨架重构
3. 几乎全部应用配置接入 UI
4. 性能优化
5. 完整回归

## 12. 设计结论

本次重构将以“配置中心重构”为主轴，在不改变核心功能逻辑的前提下，完成：

1. 配置模型与配置接口收敛
2. 配置页从半成品升级为完整配置中心
3. 几乎全部应用级配置页面化管理
4. 渐进式性能优化与逐步验证

整个过程遵循“先契约、后页面、再性能、每步测试”的策略，以最小风险完成大幅结构优化。
